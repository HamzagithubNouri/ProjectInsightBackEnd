# ProjectInsight AI — Backend
 
An AI-powered platform that assists instructors in monitoring student integration projects, combining GitHub activity tracking with automated LLM-based code review (LangChain + Ollama).
 
> Built as part of an RDI internship (Subject #80) at ESPRIT, supervised by **Mr. Ghassen Fodha**.
 
---
 
## 🎯 Purpose
 
ProjectInsight AI enables:
- **Teachers** to track each student's progress and contribution within a team project (commits, pull requests, GitHub activity),
- **Students** to receive **automated pedagogical feedback** on their code quality and security, generated by LLMs running fully locally.
The system supports three roles: **Admin** (university), **Teacher**, and **Student**.
 
---
 
## 🏗️ Architecture
 
```
Angular (Frontend)  →  FastAPI (Backend)  →  PostgreSQL (business data)
                              │
                              ├──► GitHub API (OAuth, contributions)
                              │
                              └──► AI Pipeline (LangChain / LCEL)
                                      ├─ Ollama (local inference, no external calls)
                                      └─ ChromaDB (vector store for RAG)
```
 
- **PostgreSQL**: source of truth for users, teams, classes, and reviews.
- **ChromaDB**: semantic search layer only (pedagogical knowledge base + review history).
- **LangChain (LCEL)**: orchestrates the code review pipeline (prompt → LLM → structured parsing).
- **Ollama**: all LLM inference runs locally — no data ever leaves the machine.

## 🤖 AI Code Review Pipeline
 
The review module (`ai_review_service.py`) is built on a **LangChain LCEL** chain:
 
1. Submitted code (pasted or uploaded) is analyzed by the review LLM (`ChatOllama`).
2. Results are validated through `PydanticOutputParser` + `OutputFixingParser` (auto-correction of malformed JSON).
3. For **critical/high** severity findings, a dedicated enrichment chain (`_enrich_chain`) generates an explanation, an example, and a suggested fix, grounded in a RAG knowledge base (27 Markdown sheets covering security, maintainability, code quality, and performance).
4. Generated code fixes go through syntax validation (`ast.parse`) with a single automatic retry on failure.
Two separate endpoints:
- `POST /ai-review/analyze` → review + score
- `POST /ai-review/fix` → full file correction (on demand)

## 🚀 Setup & Getting Started
 
### Prerequisites
- Python 3.10+
- PostgreSQL
- [Ollama](https://ollama.com) installed and running locally
- A configured GitHub OAuth App
### 1. Clone the repository
```bash
git clone https://github.com/HamzagithubNouri/ProjectInsightBackEnd.git
cd ProjectInsightBackEnd
```
 
### 2. Create a virtual environment and install dependencies
```bash
python -m venv venv
source venv/bin/activate   # or venv\Scripts\activate on Windows
pip install -r requirements.txt --break-system-packages
```
 
### 3. Configure environment variables
Create a `.env` file at the project root:
```env
DATABASE_URL=postgresql://user:password@localhost:5432/projectinsight
SECRET_KEY=change_me
GITHUB_CLIENT_ID=xxx
GITHUB_CLIENT_SECRET=xxx
GITHUB_REDIRECT_URI=http://localhost:8000/auth/github/callback
FRONTEND_URL=http://localhost:4200
OLLAMA_URL=http://localhost:11434
```
 
### 4. Pull the required Ollama models
```bash
ollama pull qwen2.5-coder:7b
ollama pull deepseek-coder-v2:16b
ollama pull nomic-embed-text
```
 
### 5. Create the Admin account
```bash
python create_admin.py
```
 
### 6. Run the server
```bash
uvicorn app.main:app --reload
```
 
The API is available at `http://localhost:8000` (Swagger docs at `http://localhost:8000/docs`).

## 📌 Key Architectural Decisions
 
- Strict separation between models / schemas / routes / services (no business logic in routers).
- The LLM **never** generates structural finding metadata (title, severity) — it only produces the pedagogical enrichment, which is re-injected by Python code to prevent hallucination of already-validated data.
- Teacher-facing endpoints are **read-only** and never trigger the LangChain pipeline.
- Two separate ChromaDB vector stores: one for the static knowledge base (27 sheets), one for the dynamic review history.
